# V0.3 回滚计划（第五轮修订版）

> 基线：phase1 @ d39c7aa。  
> 保存在 AndroidHarness 独立工作区 `v03_planning/`，**不修改 bb-node 仓库**。
> **本文档中的命令仅为操作方案示例，不构成本轮任何执行授权。**

---

## 1. 回滚原则（删除危险的默认方案）

| 禁止事项 | 说明 |
|---|---|
| 禁止默认执行 `rm -rf` | 任何回滚不得默认删除目录，尤其是 RAW 目录和数据库目录 |
| 禁止默认 `reset main` | Git 回滚不得默认执行 `git reset --hard main` |
| 禁止直接覆盖原始数据库 | 数据库恢复不得直接覆盖原 `.db` 文件，应使用新路径验证后再切换 |
| 禁止删除 RAW 或未提交工作区文件 | RAW 文件和未提交文件必须只读保留，不得删除 |
| 禁止只复制代码文件就认为历史已归档 | Git 历史必须通过可恢复的提交对象和 Tag 保存 |

| 优先采用 | 说明 |
|---|---|
| 新目录 | 备份和恢复使用新目录，不覆盖原有目录 |
| 数据库副本 | 迁移和测试在数据库副本上执行，不直接操作生产库 |
| 独立迁移目标 | 迁移目标独立于生产路径，验证后再切换 |
| 验证后切换路径 | 恢复的数据库文件必须验证完整后，才切换为生产路径 |
| 原始资产只读保留 | 原始数据库、RAW 文件、未提交文件均只读保留 |

---

## 2. 回滚范围

| 阶段 | 回滚对象 | 回滚触发条件 |
|---|---|---|
| 阶段 0 | 只读资产盘点、备份可行性评估 | 无法确认数据库路径、磁盘空间不足、WAL 状态异常 |
| 阶段 1 | 基线决议 | 用户反对基线选择 |
| 阶段 2 | 修复筛选清单 | 某个修复风险过高、需进一步评审 |
| 阶段 3 | 目标目录新代码 | 采集链路运行失败、发现新缺陷 |
| 阶段 4 | 数据库迁移、RAW 迁移 | 校验失败、生产库迁移失败 |
| 阶段 5 | 导出模块 | 导出失败、数据格式错误 |
| 阶段 6 | 客户端架构规划 | 客户端架构无法与核心库解耦 |
| 阶段 7 | 验收结果 | 有失败项未整改 |
| 阶段 8 | 分支合并、分支删除 | 合并冲突、误删有价值代码 |

---

## 3. 阶段 0 回滚：只读资产盘点

阶段 0 为只读评估，无需回退文件。如无法确认数据库路径、磁盘空间不足或 WAL 状态异常，停止操作、补充调查、重新评估。

---

## 4. 阶段 1-3 回滚（决策与代码整理）

- **阶段 1**：撤销基线决议，恢复到“未确定”状态，重新评审。
- **阶段 2**：移除高风险修复，更新筛选清单，不修改源代码。
- **阶段 3**：删除目标目录中的新代码，恢复到阶段 2 状态，原有源代码不受影响。

## 5. 阶段 4 回滚：数据库与 RAW 数据迁移（最关键）

### 5.1 触发条件

- 迁移前后行数不一致
- 表结构、索引、外键不一致
- 数据核验失败（未变更表规范化数据核验失败，或变更表数据映射核验失败）
- RAW 文件 SHA256 不一致
- 生产库迁移失败导致数据库损坏
- 采集程序无法读取迁移后的数据库

### 5.2 回滚动作（R5 明确拆分为三个授权层次）

> **本节所有命令仅为操作方案示例，不构成执行授权。每个层次的操作必须获得针对本次恢复任务的明确人工授权。**

#### A 层：回滚前准备（仅只读检查，不执行任何文件恢复或路径切换）

```
步骤 1：立即停止所有采集与数据库写入程序
步骤 2：只读检查数据库、WAL、SHM 状态
        - sqlite3 <db_path> "PRAGMA integrity_check;"
        - ls -la <db_path>*
步骤 3：只读检查 RAW 目录状态
        - find <raw_path> -type f -exec sha256sum {} \;
步骤 4：确认备份来源、目标路径、磁盘空间充足
        - ls -la ./backup/<timestamp>/
        - df -h <target_disk>
步骤 5：记录当前状态，等待 B 层授权
```

**A 层严禁**：执行任何文件重命名、复制、移动、路径切换、删除操作。

#### B 层：实际恢复操作（必须获得针对本次恢复任务的明确人工授权）

以下操作**逐项**需要明确授权，授权前不得执行：

```
B1：将迁移失败的数据库文件改名（保留失败副本，不删除）
    mv <db_path> <db_path>.migration_failed_<timestamp>

B2：从备份恢复数据库文件到新路径（不直接覆盖原文件）
    使用 SQLite online backup API 或经停写+检查点的备份文件
    恢复到 <db_path>.restored_<timestamp>

B3：验证恢复完整性（仅只读检查，作为切换前置条件）
    - 备份文件完整性 SHA256 与备份时记录一致（仅验证备份未损坏）
    - 所有表行数与备份前一致
    - 表结构与备份前一致
    - RAW 文件 SHA256 与备份前一致

B4：将恢复文件切换到生产路径（经用户确认后）
    mv <db_path>.restored_<timestamp> <db_path>

B5：从备份恢复 RAW 目录到新路径（不删除原目录）
    cp -r ./backup/<timestamp>/data/raw/ ./data/raw.restored_<timestamp>

B6：验证 RAW 文件 SHA256 与备份前一致（仅只读检查）

B7：切换 RAW 生产路径（经用户确认后）
    mv <raw_path> <raw_path>.pre_rollback_<timestamp>
    mv <raw_path>.restored_<timestamp> <raw_path>
```

**B 层所有操作必须遵守**：
- 不覆盖原始资产（原始数据库、RAW 目录均保留为 `.pre_rollback_` 或 `.migration_failed_` 副本）
- 使用新路径（`.restored_<timestamp>`）进行恢复和验证
- 保留失败副本，不自动删除旧数据
- 验证完成后再决定是否切换生产路径
- 每个切换动作（B4、B7）需单独获得人工确认

#### C 层：恢复后验证（首先只读检查，读写验证需另行授权）

```
C1：仅只读检查
    - 启动采集程序进行只读查询（表结构、行数、关键数据）
    - 确认数据库可正常打开、查询、WAL 模式正常

C2：如需启动采集程序或进行真实写入验证，必须另行获得人工授权
    - 授权范围明确限定为：本次回滚后的验证任务
    - 执行最小化采集干跑或测试写入
    - 仅验证读写链路通畅，不产生业务数据
    - 验证完成后立即停止，不作为默认回滚步骤

C3：验证通过后，标记回滚完成
```

**C 层要求**：
- 首先只读检查（C1），无需额外授权
- 任何真实读写验证（C2）必须**单独获得人工授权**，不得作为默认回滚步骤
- 验证失败不自动触发进一步回滚，需人工决策

### 5.3 验证标准

- 备份文件完整性 SHA256 与备份时一致（仅验证备份文件未损坏，**不作为迁移前后数据库相同的判断标准**）
- 所有表行数、结构、索引与备份前一致
- 所有 RAW 文件 SHA256 与备份前一致
- 采集程序可正常启动并读写数据（仅在阶段二授权验证时）

### 5.4 预防措施

1. 迁移前使用 SQLite online backup API 或明确停写 + WAL 检查点流程创建一致性备份
2. 在数据库副本上执行迁移脚本测试，验证无误
3. 每个迁移脚本在单个事务中执行，失败自动回滚
4. 迁移脚本必须具备结构检测和兼容性判断（见 V03_DATA_MIGRATION_PLAN §5.1）
5. 生产迁移必须单独获得用户批准
6. 数据核验按 V03_DATA_MIGRATION_PLAN §8 执行：未变更表规范化数据核验，变更表明确的数据映射核验；不得在未定义稳定排序方式时直接使用 `ORDER BY rowid`

## 6. 阶段 5-7 回滚

- **阶段 5**：删除或禁用 export/ 模块，恢复到阶段 4 状态，核心采集不受影响
- **阶段 6**：删除或禁用 client/ 目录中的有问题代码，恢复到阶段 5 状态
- **阶段 7**：暂停阶段 8，制定整改计划；B1-B4 未确认不阻塞基础采集和 RAW 保存的验收，但未确认数据不得作为已确认数据进入 Unified；B5/B6 未修复则阻塞相关写入链路启用

---

## 7. 阶段 8 回滚：分支收敛

**触发条件**：合并冲突、误删有价值代码、远程分支处理错误。

**回滚动作**：
1. 停止所有 Git 操作
2. 如分支已删除，从备份或远程仓库恢复
3. 如合并有问题，回退到合并前状态（需用户批准，**不默认执行 reset main**）
4. 确认 archive/ 目录和 Git Tag 中已保存所有旧分支的有价值代码和审计证据
5. **Git 历史通过可恢复的提交对象和 Tag 保存，不得只复制代码文件就认为历史已经归档**
6. 重新执行阶段 8

## 8. 数据库与 RAW 备份恢复参考

### 8.1 备份前检查清单

- [ ] 所有数据库文件已列出并分类（生产/审计附件/测试）
- [ ] 所有 RAW 文件已列出
- [ ] 备份目录已创建（新目录，不覆盖现有备份）
- [ ] 磁盘空间充足
- [ ] WAL/SHM 状态已确认
- [ ] 写入进程状态已确认

### 8.2 备份方式（WAL 一致性）

| 方式 | 说明 | 前提条件 |
|---|---|---|
| **SQLite online backup API**（推荐） | 使用 `sqlite3.Connection.backup()` 或等价 API | 数据库可正常打开 |
| **明确停写 + WAL 检查点** | 停止所有写入，执行 `PRAGMA wal_checkpoint(TRUNCATE)` 成功后复制文件 | 必须确保无写入进程 |

**禁止**：在有活跃写入进程时直接复制 WAL 模式数据库文件而不执行检查点或 online backup。

### 8.3 恢复原则

1. 恢复到新路径，不直接覆盖原文件
2. 验证恢复完整性（备份文件完整性 SHA256、行数、结构）
3. 经用户确认后切换为生产路径
4. RAW 恢复到新目录，不删除原目录
5. 所有恢复操作必须记录

## 10. 禁止事项（回滚期间）

- 回滚期间不得修改、删除或覆盖任何原有源代码
- 回滚期间不得运行可能写入数据库的程序（阶段一严禁，阶段二需单独授权）
- 回滚期间不得创建、删除或修改 Git 分支
- 回滚期间不得 commit、push、merge、rebase、reset、clean
- 工作区未提交修改不得被覆盖
- 回滚不得默认执行 rm -rf，不得默认 reset main，不得直接覆盖原始数据库，不得删除 RAW 文件
- 数据库文件 SHA256 仅用于备份完整性验证，不作为迁移前后数据库相同的判断标准
- 不得将回滚后的读写验证默认为回滚操作的一部分
